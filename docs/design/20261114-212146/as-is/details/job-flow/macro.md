# 매크로 Job Flow — 주문 관리 시스템과 외부의 협력 (AS-IS)

## 관찰 경계

- **대상 시스템 `주문관리시스템`**은 Medusa 서버(`packages/medusa`)와 관리자 대시보드, 그리고 이 둘이 쓰는 모듈을 한 객체로 묶은 것이다. 포함 범위는 다음과 같다.
  - 서버: API 라우트, 워크플로 엔진, 주문·결제·이행·재고·고객·알림 모듈, 이벤트 버스, DB.
  - 관리자 대시보드: 서버가 `/app`에서 서빙한다.
  - 내부 구성은 [system.md](system.md)에서 펼친다.
- **외부 객체**
  - `운영자`: 관리자 대시보드를 쓰는 관리자 역할.
  - `고객`: 스토어프런트를 통해 주문하고 결제 링크와 이전 요청을 처리하는 구매자.
  - `결제대행사`: Stripe 등 결제 제공자.
  - `이행대행사`: 이행 제공자(fulfillment provider). 기본값은 manual이고, 외부 배송사 연동일 수 있다.
  - `파일저장소`: 파일 제공자. local 또는 S3.
- **이번 범위에서 빠진 것**
  - 스토어프런트 화면 자체.
  - 고객 알림 발송. 코어에 기본 제공되는 구독자는 `order.created` 이메일 하나뿐이다. 반품, 출고, 편집 같은 이벤트를 고객에게 알릴지는 애플리케이션이 직접 구독해서 정한다. 그래서 아래 그림의 고객 쪽 메시지는 `업무이벤트발행`까지만 그리고, 그 뒤 실제로 알림이 나가는지는 앱 구성에 달려 있다고 적는다.
- 각 그림 아래 설명 목록은 화살표 하나에 문장 하나씩, 관계 선언 순서대로 적는다. 메서드에서 결과로 들어가는 연결은 설명하지 않는다.

## M1. 주문 접수(경계만)

```jobflow
scope: 고객 주문이 주문관리시스템에 접수되는 경계
Object: 고객, 주문관리시스템, 결제대행사
고객.On주문완료 --> 주문관리시스템.message.장바구니완료요청
주문관리시스템.message.장바구니완료요청 --> 주문관리시스템.주문생성검사
주문관리시스템.주문생성검사.결제승인필요 --> 결제대행사.message.결제승인요청
결제대행사.message.결제승인요청 --> 주문관리시스템.message.결제승인결과
주문관리시스템.message.결제승인결과 --> 고객.message.주문접수결과
```

- 고객이 스토어프런트에서 주문을 마치면 시스템에 장바구니 완료를 요청한다.
- 시스템은 장바구니의 결제 상태를 검사하고 주문을 만든다.
- 결제 승인이 필요하면 결제대행사에 결제 세션 승인을 요청한다.
- 결제대행사는 승인 결과를 시스템에 돌려준다.
- 시스템은 고객에게 주문 접수 결과를 돌려준다. 이때 `order.placed` 이벤트가 발행된다. 이 단계는 관리자 화면 범위 밖이며, 관리자 쪽 흐름의 출발점이 되는 주문이 여기서 생긴다.

## M2. 출고·배송·배달

```jobflow
scope: 운영자의 출고 처리와 이행대행사 협력
Object: 운영자, 주문관리시스템, 이행대행사, 고객
운영자.On출고요청 --> 주문관리시스템.message.출고생성요청
주문관리시스템.message.출고생성요청 --> 주문관리시스템.출고검사
주문관리시스템.출고검사.출고가능 --> 이행대행사.message.이행생성요청
주문관리시스템.출고검사.출고불가 --> 운영자.message.출고거절
이행대행사.message.이행생성요청 --> 주문관리시스템.message.이행생성결과
주문관리시스템.message.이행생성결과 --> 운영자.message.출고완료
주문관리시스템.message.이행생성결과 --> 고객.message.업무이벤트발행
운영자.On배송처리 --> 주문관리시스템.message.배송등록요청
주문관리시스템.message.배송등록요청 --> 운영자.message.배송등록완료
운영자.On배달확인 --> 주문관리시스템.message.배달완료요청
주문관리시스템.message.배달완료요청 --> 운영자.message.배달완료등록
```

- 운영자가 출고를 시작하면 시스템에 출고 생성을 요청한다. 위치, 배송 옵션, 품목 수량을 함께 보낸다.
- 시스템은 주문 상태와 품목 수량, 배송 옵션을 검사한다.
- 출고할 수 있으면 이행대행사에 이행 생성을 요청한다.
- 출고할 수 없으면(취소된 주문, 수량 초과 등) 운영자에게 거절 사유를 돌려준다.
- 이행대행사는 이행 데이터와 라벨을 담은 생성 결과를 시스템에 돌려준다.
- 시스템은 재고를 조정하고 예약을 갱신한 뒤 운영자에게 출고 완료를 알린다.
- 같은 결과로 `order.fulfillment_created`를 발행한다. 고객에게 알림이 가는지는 앱 구독자에 달려 있다.
- 운영자가 송장 번호를 입력해 배송을 처리하면 시스템에 배송 등록을 요청한다. 코어 워크플로는 이 단계에서 이행대행사를 부르지 않는다.
- 시스템은 배송을 기록하고 `shipment.created`를 발행한 뒤 완료를 돌려준다.
- 운영자가 배달을 확인하면 시스템에 배달 완료를 요청한다.
- 시스템은 주문 단위 잠금 아래에서 배달을 기록하고 `delivery.created`를 발행한 뒤 결과를 돌려준다.

## M3. 결제 매입·환불·미결 금액 수납

```jobflow
scope: 결제 매입과 환불, 미결 금액 수납
Object: 운영자, 고객, 주문관리시스템, 결제대행사
운영자.On매입요청 --> 주문관리시스템.message.결제매입요청
주문관리시스템.message.결제매입요청 --> 결제대행사.message.매입요청
결제대행사.message.매입요청 --> 주문관리시스템.message.매입결과
주문관리시스템.message.매입결과 --> 운영자.message.매입결과안내
운영자.On환불요청 --> 주문관리시스템.message.환불요청
주문관리시스템.message.환불요청 --> 주문관리시스템.환불가능검사
주문관리시스템.환불가능검사.매입액이내 --> 결제대행사.message.환불요청
주문관리시스템.환불가능검사.매입액초과 --> 운영자.message.환불거절
결제대행사.message.환불요청 --> 주문관리시스템.message.환불결과
주문관리시스템.message.환불결과 --> 운영자.message.환불완료안내
운영자.On결제링크전달 --> 고객.On결제링크수신
고객.On결제링크수신 --> 주문관리시스템.message.결제컬렉션결제요청
운영자.On결제완료표시 --> 주문관리시스템.message.결제완료표시요청
주문관리시스템.message.결제완료표시요청 --> 운영자.message.결제완료표시결과
```

- 운영자가 매입을 시작하면 시스템에 결제 매입을 요청한다.
- 시스템은 결제대행사에 매입을 요청한다. 매입 단계에는 보상 처리가 없다.
- 결제대행사는 매입 결과를 돌려준다.
- 시스템은 주문 거래를 기록하고 `payment.captured`를 발행한 뒤 운영자에게 결과를 알린다.
- 운영자가 환불을 시작하면 시스템에 환불을 요청한다. 금액, 사유, 메모를 함께 보낸다.
- 시스템은 요청 금액이 매입액에서 이미 환불한 금액을 뺀 범위 안인지 검사한다.
- 범위 안이면 결제대행사에 환불을 요청한다.
- 범위를 넘으면 "You are not allowed to refund more than the captured amount"로 거절한다.
- 결제대행사는 환불 결과를 돌려준다.
- 시스템은 거래를 기록하고 `payment.refunded`를 발행한 뒤 운영자에게 결과를 알린다.
- 운영자가 대시보드에서 복사한 결제 링크를 시스템 밖의 수단으로 고객에게 전달한다. 링크 전달은 데이터가 아니라 운영자의 행동이다.
- 고객은 링크로 스토어프런트에 들어와 결제 컬렉션을 결제한다. 이후 결제 흐름은 스토어 범위다.
- 운영자가 결제 완료를 표시하면 시스템에 결제 완료 표시를 요청한다.
- 시스템은 시스템 결제 제공자로 세션을 만들고, 승인한 뒤 바로 매입해서 결과를 돌려준다. 외부 결제대행사는 관여하지 않는다.

## M4. 반품 요청과 수령

```jobflow
scope: 반품 요청 확정과 실물 수령 처리
Object: 운영자, 주문관리시스템, 이행대행사, 고객
운영자.On반품확정 --> 주문관리시스템.message.반품요청확정
주문관리시스템.message.반품요청확정 --> 주문관리시스템.반품배송판정
주문관리시스템.반품배송판정.반품배송있음 --> 이행대행사.message.반품이행생성요청
주문관리시스템.message.반품요청확정 --> 운영자.message.반품요청결과
주문관리시스템.message.반품요청확정 --> 고객.message.업무이벤트발행
고객.On반품물품발송 --> 운영자.On반품물품도착
운영자.On반품물품도착 --> 주문관리시스템.message.반품수령확정
주문관리시스템.message.반품수령확정 --> 운영자.message.반품수령결과
```

- 운영자가 반품 드래프트를 확정하면 시스템에 반품 요청 확정을 보낸다. 드래프트를 만들고 품목을 편집하는 요청은 시스템 안의 일이라 생략했다.
- 시스템은 반품 배송 옵션이 지정되어 있는지 판단한다.
- 지정되어 있으면 이행대행사에 반품용 이행 생성을 요청하고, 그 결과를 반품과 연결한다.
- 시스템은 주문 변경을 확정하고 결제 컬렉션을 갱신한 뒤 운영자에게 결과를 돌려준다.
- 같은 확정으로 `order.return_requested`를 발행한다.
- 고객이 물품을 보내면 운영자 쪽에 물품이 도착하는 실물 사건이 생긴다. 이것은 데이터 전달이 아니며, 시스템에 자동으로 기록되지 않는다.
- 운영자가 받은 수량과 손상 수량을 입력해 확정하면 시스템에 반품 수령 확정을 보낸다.
- 시스템은 손상되지 않은 수량만큼 재고를 늘리고, 결제 컬렉션을 갱신하고, `order.return_received`를 발행한 뒤 결과를 돌려준다. 환불은 자동으로 되지 않는다. 운영자가 [M3](#m3-결제-매입환불미결-금액-수납)의 환불을 따로 해야 한다.

## M5. 클레임·교환 확정

```jobflow
scope: 클레임과 교환의 확정
Object: 운영자, 주문관리시스템, 이행대행사, 고객
운영자.On클레임교환확정 --> 주문관리시스템.message.클레임교환확정요청
주문관리시스템.message.클레임교환확정요청 --> 주문관리시스템.확정내용판정
주문관리시스템.확정내용판정.반품배송있음 --> 이행대행사.message.반품이행생성요청
주문관리시스템.message.클레임교환확정요청 --> 운영자.message.클레임교환확정결과
주문관리시스템.message.클레임교환확정요청 --> 고객.message.업무이벤트발행
```

- 운영자가 클레임이나 교환을 확정하면 시스템에 확정을 요청한다.
- 시스템은 돌려받을 품목의 반품 배송이 있는지 판단한다. 새로 보낼 품목이 있으면 재고 예약은 시스템 안에서 처리한다.
- 반품 배송이 있으면 이행대행사에 반품용 이행 생성을 요청한다.
- 시스템은 주문 변경을 확정하고 결제 컬렉션을 갱신한 뒤 결과를 돌려준다. 새로 보낼 품목은 이후 [M2](#m2-출고배송배달)의 출고 흐름으로 처리한다.
- `order.claim_created` 또는 `order.exchange_created`를 발행한다.

## M6. 주문 편집 요청과 확정

```jobflow
scope: 주문 편집의 요청과 확정
Object: 운영자, 주문관리시스템, 고객
운영자.On편집요청 --> 주문관리시스템.message.편집요청
주문관리시스템.message.편집요청 --> 운영자.message.편집요청결과
주문관리시스템.message.편집요청 --> 고객.message.업무이벤트발행
운영자.On편집강제확정 --> 주문관리시스템.message.편집확정요청
주문관리시스템.message.편집확정요청 --> 주문관리시스템.편집확정검사
주문관리시스템.편집확정검사.확정가능 --> 운영자.message.편집확정결과
주문관리시스템.편집확정검사.확정불가 --> 운영자.message.편집확정거절
```

- 운영자가 편집 내용을 요청하면 시스템에 편집 요청을 보낸다.
- 시스템은 주문 단위 잠금 아래에서 변경을 `requested` 상태로 바꾸고 결과를 돌려준다.
- 같은 요청으로 `order-edit.requested`를 발행한다. 고객이 이것을 받아 수락하는 경로가 있는지는 이번 범위에서 확인하지 않았다.
- 운영자가 상세 화면에서 강제 확정을 누르면 시스템에 편집 확정을 요청한다.
- 시스템은 변경이 확정할 수 있는 상태인지 검사한다.
- 확정할 수 있으면 변경을 적용하고, 예약을 다시 잡고, 결제 컬렉션을 갱신하고, `order-edit.confirmed`를 발행한 뒤 결과를 돌려준다.
- 확정할 수 없으면 거절 사유를 돌려준다.

## M7. 소유권 이전

```jobflow
scope: 주문 소유권 이전 요청과 게스트 이전
Object: 운영자, 주문관리시스템, 고객
운영자.On소유권이전 --> 주문관리시스템.message.소유권이전요청
주문관리시스템.message.소유권이전요청 --> 주문관리시스템.이전방식판정
주문관리시스템.이전방식판정.등록고객 --> 고객.message.이전요청이벤트
주문관리시스템.이전방식판정.등록고객 --> 운영자.message.이전요청접수
주문관리시스템.이전방식판정.게스트 --> 운영자.message.게스트이전완료
고객.On이전수락 --> 주문관리시스템.message.이전수락요청
주문관리시스템.message.이전수락요청 --> 주문관리시스템.이전토큰검사
주문관리시스템.이전토큰검사.유효 --> 고객.message.이전완료
운영자.On이전요청취소 --> 주문관리시스템.message.이전요청취소
주문관리시스템.message.이전요청취소 --> 운영자.message.이전요청취소결과
```

- 운영자가 소유권 이전을 시작하면 시스템에 이전을 요청한다. 대상은 등록 고객 ID 또는 게스트 이메일이다.
- 시스템은 이전 방식을 판정한다.
- 등록 고객이면 토큰을 담은 `transfer` 변경을 만들고 `order.transfer_requested`를 발행한다. 고객에게 실제로 알리는 일은 앱 구독자 몫이다.
- 등록 고객이면 운영자에게 요청 접수만 알린다. 소유권은 아직 바뀌지 않았다.
- 게스트이면 고객을 찾거나 새로 만들어 즉시 이전을 확정하고 완료를 알린다.
- 고객이 스토어에서 수락하면 시스템에 수락을 요청한다.
- 시스템은 토큰을 검사한다.
- 토큰이 유효하면 변경을 확정하고 고객에게 결과를 돌려준다. 거절 경로(decline)는 스토어 API에 있으며 이 그림에서는 생략했다.
- 운영자가 요청을 취소하면 시스템에 취소를 보낸다.
- 시스템은 변경을 삭제하고 결과를 돌려준다.

## M8. 주문 취소

```jobflow
scope: 주문 취소와 결제 정리
Object: 운영자, 주문관리시스템, 결제대행사
운영자.On주문취소 --> 주문관리시스템.message.주문취소요청
주문관리시스템.message.주문취소요청 --> 주문관리시스템.취소가능검사
주문관리시스템.취소가능검사.취소가능 --> 결제대행사.message.매입분환불요청
주문관리시스템.취소가능검사.취소가능 --> 결제대행사.message.미매입결제취소요청
주문관리시스템.취소가능검사.취소불가 --> 운영자.message.주문취소거절
결제대행사.message.매입분환불요청 --> 주문관리시스템.message.환불결과
주문관리시스템.message.환불결과 --> 운영자.message.주문취소완료
```

- 운영자가 주문 취소를 확인하면 시스템에 취소를 요청한다.
- 시스템은 주문이 완료되었거나 이미 취소되었는지, 취소되지 않은 이행이 남았는지 검사한다.
- 취소할 수 있으면 매입된 결제를 환불해 달라고 결제대행사에 요청한다.
- 같은 판단으로 아직 매입되지 않은 결제의 취소도 요청한다. 이 결과는 실패해도 로그만 남기고 흐름을 막지 않는다.
- 취소할 수 없으면 사유를 돌려준다. 예를 들어 이행이 남아 있으면 먼저 이행을 취소해야 한다.
- 환불 결과가 오면 시스템은 예약을 지우고, 크레딧 라인을 정리하고, 주문을 취소 상태로 바꾸고, `order.canceled`를 발행한 뒤 운영자에게 완료를 알린다.

## M9. 주문 목록 내보내기

```jobflow
scope: 주문 CSV 내보내기
Object: 운영자, 주문관리시스템, 파일저장소
운영자.On내보내기 --> 주문관리시스템.message.주문내보내기요청
주문관리시스템.message.주문내보내기요청 --> 운영자.message.내보내기접수
주문관리시스템.message.주문내보내기요청 --> 파일저장소.message.CSV업로드
파일저장소.message.CSV업로드 --> 주문관리시스템.message.파일주소
주문관리시스템.message.파일주소 --> 운영자.message.내보내기완료알림
```

- 운영자가 목록 필터를 정해 내보내기를 요청하면 시스템에 내보내기를 요청한다.
- 시스템은 `transaction_id`를 담은 202로 접수를 먼저 알린다.
- 시스템은 백그라운드 워크플로에서 주문을 페이지 단위로 읽어 CSV로 바꾸고, 파일저장소에 스트림으로 올린다.
- 파일저장소는 업로드한 파일의 주소를 돌려준다.
- 시스템은 `feed` 채널 알림(`admin-ui` 템플릿)에 파일을 붙여 운영자에게 완료를 알린다. 실패하면 실패 알림을 보낸다.
