# 시스템 Job Flow — 주문관리시스템 내부 서비스 협력 (AS-IS)

## 서비스 구분

Medusa는 하나의 프로세스로 배포하는 모듈형 모놀리스다. 이 문서는 Method-R 시스템 깊이에 따라 **책임과 데이터 소유가 나뉜 모듈과 앱 각각을 하나의 서비스로** 보고 그린다.

- 각 모듈은 자기 테이블만 소유하고, 다른 모듈의 데이터를 직접 바꾸지 않는다.
- 모듈 사이의 연결은 워크플로가 조율하고, 모듈 간 관계 데이터는 링크 모듈이 맡는다.

| 그림 이름 | 구현 | 책임·소유 데이터 | 상세 문서 |
| --- | --- | --- | --- |
| 관리화면 | `packages/admin/dashboard` (React SPA) | 화면 상태와 React Query 캐시. 서버 데이터는 소유하지 않는다 | [admin-dashboard.md](admin-dashboard.md) |
| 주문워크플로 | `packages/medusa/src/api/admin/**` 라우트와 `packages/core/core-flows` 워크플로(워크플로 엔진 위에서 실행) | 요청 검증, RBAC, 단계 순서, 보상(롤백), 이벤트 그룹. 영속 데이터는 소유하지 않는다 | [order-workflows.md](order-workflows.md) |
| 주문 | `packages/modules/order` | 주문, 품목(버전 관리), 주문 변경과 그 액션, 반품, 클레임, 교환, 거래, 크레딧 라인, 요약 | [order-module.md](order-module.md) |
| 결제 | `packages/modules/payment`와 결제 제공자 | 결제 컬렉션, 세션, 결제, 매입, 환불, 환불 사유 | [payment-module.md](payment-module.md) |
| 이행 | `packages/modules/fulfillment`와 이행 제공자 | 이행, 이행 품목, 라벨, 배송 옵션·프로필, 서비스 존 | [fulfillment-module.md](fulfillment-module.md) |
| 재고 | `packages/modules/inventory`(+ stock-location) | 재고 항목, 위치별 재고 수준, 예약 | [inventory-module.md](inventory-module.md) |
| 이벤트버스 | event-bus-local 또는 event-bus-redis | 그룹으로 묶인 이벤트를 워크플로가 끝난 뒤 전달 | 이 문서 |

- **링크 모듈**: 모듈 간 관계는 링크 테이블로만 표현한다(`order_fulfillment`, `return_fulfillment`, `order_payment_collection`, `order_claim_payment_collection`, `order_exchange_payment_collection`). 주문 모듈은 결제·이행 테이블을 모른다.
- **조율 방식**: 관리자가 하는 변경은 모두 주문워크플로가 Orchestration으로 처리한다.
- **업무 이벤트**: `order.*`, `payment.*`, `shipment.created` 등은 Choreography 방식으로 발행만 한다. 코어에는 이 이벤트를 받아 업무를 이어 가는 구독자가 없다. 기본 구독자는 `order.created` 알림, 결제 웹훅, 검색 색인뿐이다.
- **관리화면과 서버**: 관리화면은 서버와 HTTP로만 통신한다(`@medusajs/js-sdk`, 세션 인증). 그래서 아래 그림에서 관리화면의 요청은 받는 쪽 이벤트인 `주문워크플로.On…요청`으로 시작한다. 화면 응답과 쿼리 무효화는 [admin-dashboard.md](admin-dashboard.md)에 있다.

## S1. 출고 생성

```jobflow
scope: 출고 생성 시 서비스 협력
Object: 주문워크플로, 주문, 이행, 재고, 이벤트버스
주문워크플로.On출고생성요청 --> 주문.message.출고대상주문조회
주문.message.출고대상주문조회 --> 주문워크플로.message.주문데이터
주문워크플로.message.주문데이터 --> 주문워크플로.출고검사
주문워크플로.출고검사.출고가능 --> 이행.message.이행생성요청
이행.message.이행생성요청 --> 주문워크플로.message.이행생성됨
주문워크플로.message.이행생성됨 --> 재고.message.재고수준조정요청
주문워크플로.message.이행생성됨 --> 주문.message.이행등록요청
주문워크플로.message.이행생성됨 --> 재고.message.예약갱신요청
주문워크플로.message.이행생성됨 --> 이벤트버스.message.출고생성이벤트
```

- 관리화면이 출고 생성을 요청하면, 주문워크플로가 주문 서비스에서 품목·배송 방법·예약 정보를 읽는다.
- 주문 서비스가 주문 데이터를 돌려준다.
- 주문워크플로가 출고 가능 여부를 검사한다. 취소된 주문, 수량 초과, 배송 프로필 불일치를 확인하며, 하나라도 걸리면 화면에 오류를 돌려주고 끝난다.
- 출고할 수 있으면 이행 서비스에 이행 생성을 요청한다. 이행 서비스는 제공자의 `createFulfillment`를 호출한다.
- 이행 서비스가 생성한 이행을 돌려준다.
- 주문워크플로가 재고 서비스에 출고 위치의 재고 수준을 줄여 달라고 요청한다.
- 이와 병렬로 주문 서비스에 이행 등록을 요청하고 `order_fulfillment` 링크를 만든다.
- 같은 단계에서 재고 서비스에 출고 수량만큼 예약을 줄이거나 지워 달라고 요청한다.
- 이벤트버스에 `order.fulfillment_created`를 묶어 둔다. 이 이벤트는 워크플로가 성공으로 끝난 뒤에만 전달된다. 뒤 단계가 실패하면 보상이 등록을 되돌린다. 잠금은 쓰지 않는다.

## S2. 반품 요청 확정과 수령 확정

```jobflow
scope: 반품 요청 확정과 수령 확정의 서비스 협력
Object: 주문워크플로, 주문, 이행, 결제, 재고, 이벤트버스
주문워크플로.On반품요청확정 --> 주문.message.반품변경미리보기
주문.message.반품변경미리보기 --> 주문워크플로.message.반품미리보기
주문워크플로.message.반품미리보기 --> 주문워크플로.반품배송판정
주문워크플로.반품배송판정.반품배송있음 --> 이행.message.반품이행생성요청
주문워크플로.message.반품미리보기 --> 주문.message.주문변경확정요청
주문워크플로.message.반품미리보기 --> 결제.message.결제컬렉션갱신요청
주문워크플로.message.반품미리보기 --> 이벤트버스.message.반품요청이벤트
주문워크플로.On반품수령확정 --> 주문.message.수령변경확정요청
주문.message.수령변경확정요청 --> 주문워크플로.message.수령반영됨
주문워크플로.message.수령반영됨 --> 재고.message.재입고요청
주문워크플로.message.수령반영됨 --> 결제.message.결제컬렉션갱신요청
주문워크플로.message.수령반영됨 --> 이벤트버스.message.반품수령이벤트
```

- 관리화면이 반품 요청 확정을 보내면, 주문워크플로가 주문 서비스에 변경 미리보기를 요청한다.
- 주문 서비스는 반품 품목과 배송 액션을 반영한 미리보기를 돌려준다.
- 주문워크플로가 반품 배송 방법이 지정되어 있는지 판단한다.
- 반품 배송이 있으면 이행 서비스에 반품 이행 생성을 요청하고 `return_fulfillment` 링크를 만든다.
- 주문 서비스에 반품 품목 생성과 주문 변경 확정을 요청한다. 확정하면 주문 버전이 올라간다.
- 결제 서비스에 미결 금액에 맞춰 결제 컬렉션을 만들거나 고치거나 취소해 달라고 요청한다.
- 이벤트버스에 `order.return_requested`를 묶어 둔다.
- 관리화면이 수령 확정을 보내면, 주문워크플로가 주문 서비스에 반품 상태 갱신과 수령 변경 확정을 요청한다.
- 주문 서비스는 수령 수량과 손상 수량을 반영한 결과를 돌려준다.
- 주문워크플로가 손상되지 않은 수량만큼 재고 서비스에 재입고를 요청한다.
- 결제 서비스에 결제 컬렉션 갱신을 요청한다.
- 이벤트버스에 `order.return_received`를 묶어 둔다.
- 반품 드래프트 생성과 품목·배송·위치 편집 요청은 주문 서비스에 `pending` 상태의 변경과 액션을 쌓기만 하므로 이 그림에서는 생략했다([order-module.md](order-module.md#o1-주문-변경-수명주기)).

## S3. 매입과 환불

```jobflow
scope: 결제 매입과 환불의 서비스 협력
Object: 주문워크플로, 결제, 주문, 이벤트버스
주문워크플로.On매입요청 --> 결제.message.매입요청
결제.message.매입요청 --> 주문워크플로.message.매입완료
주문워크플로.message.매입완료 --> 주문워크플로.주문연결판정
주문워크플로.주문연결판정.주문결제 --> 주문.message.거래기록요청
주문워크플로.message.매입완료 --> 이벤트버스.message.매입이벤트
주문워크플로.On환불요청 --> 결제.message.환불가능조회
결제.message.환불가능조회 --> 주문워크플로.message.결제와환불내역
주문워크플로.message.결제와환불내역 --> 주문워크플로.환불한도검사
주문워크플로.환불한도검사.한도이내 --> 결제.message.환불요청
결제.message.환불요청 --> 주문워크플로.message.환불완료
주문워크플로.message.환불완료 --> 주문.message.거래기록요청
주문워크플로.message.환불완료 --> 이벤트버스.message.환불이벤트
```

- 관리화면이 매입을 요청하면 주문워크플로가 결제 서비스에 매입을 요청한다. 결제 서비스는 제공자의 `capturePayment`를 호출하며, 이 단계에는 보상이 없다.
- 결제 서비스가 매입 결과를 돌려준다.
- 주문워크플로가 이 결제 컬렉션이 주문에 연결되어 있는지 판단한다.
- 주문 결제이면 주문 서비스에 거래(transaction) 기록을 요청한다. 이 기록은 보상이 가능하다.
- 이벤트버스에 `payment.captured`를 묶어 둔다.
- 관리화면이 환불을 요청하면 주문워크플로가 결제 서비스에서 결제 내역을 읽는다.
- 결제 서비스가 매입 금액과 기존 환불 내역을 돌려준다.
- 주문워크플로가 요청 금액이 남은 매입액 안인지 검사한다.
  - 한도를 넘으면 `NOT_ALLOWED`로 거절하고 끝난다.
  - 이미 처리된 요청이 다시 들어온 경우(재생)에는 환불을 다시 하지 않는다.
- 한도 안이면 결제 서비스에 환불을 요청한다. 제공자의 `refundPayment`를 호출하며, 이 단계에도 보상이 없다.
- 결제 서비스가 환불 결과를 돌려준다.
- 주문 서비스에 음수 금액의 거래 기록을 요청하고, 필요하면 크레딧 라인을 만든다.
- 이벤트버스에 `payment.refunded`를 묶어 둔다. 재생인 경우에는 발행하지 않는다.

## S4. 주문 편집 요청·확정

```jobflow
scope: 주문 편집의 잠금과 확정 협력
Object: 주문워크플로, 주문, 재고, 결제, 이벤트버스
주문워크플로.On편집요청 --> 주문.message.편집변경요청상태전환
주문.message.편집변경요청상태전환 --> 이벤트버스.message.편집요청이벤트
주문워크플로.On편집확정요청 --> 주문.message.편집미리보기
주문.message.편집미리보기 --> 주문워크플로.message.편집미리보기결과
주문워크플로.message.편집미리보기결과 --> 주문워크플로.편집확정검사
주문워크플로.편집확정검사.확정가능 --> 주문.message.주문변경확정요청
주문.message.주문변경확정요청 --> 재고.message.예약재설정요청
주문.message.주문변경확정요청 --> 결제.message.결제컬렉션갱신요청
주문.message.주문변경확정요청 --> 이벤트버스.message.편집확정이벤트
```

- 편집 요청이 오면 주문워크플로가 주문 ID로 잠금을 잡고, 주문 서비스에 변경을 `requested` 상태로 바꿔 달라고 요청한다.
- 상태가 바뀌면 이벤트버스에 `order-edit.requested`를 묶어 두고 잠금을 푼다.
- 강제 확정 요청이 오면 주문워크플로가 다시 잠금을 잡고, 주문 서비스에 편집 미리보기를 요청한다.
- 주문 서비스가 미리보기를 돌려준다.
- 주문워크플로가 지금 확정할 수 있는 상태인지 검사한다.
- 확정할 수 있으면 주문 서비스에 주문 변경 확정을 요청한다.
- 확정이 끝나면 주문워크플로가 재고 서비스에 기존 예약을 지우고 새 수량으로 다시 예약해 달라고 요청한다.
- 결제 서비스에 결제 컬렉션 갱신을 요청한다.
- 이벤트버스에 `order-edit.confirmed`를 묶어 두고 잠금을 푼다.
- 편집 생성과 취소도 같은 주문 잠금을 쓴다. 반면 반품·클레임·교환·출고 워크플로는 잠금을 쓰지 않는다. 그래서 이 흐름들이 동시에 들어오면 주문 서비스의 "이미 진행 중인 주문 변경" 검사에 의존해 충돌을 막는다.

## S5. 주문 취소

```jobflow
scope: 주문 취소의 서비스 협력
Object: 주문워크플로, 주문, 결제, 재고, 이벤트버스
주문워크플로.On주문취소요청 --> 주문.message.취소대상조회
주문.message.취소대상조회 --> 주문워크플로.message.주문과이행과결제
주문워크플로.message.주문과이행과결제 --> 주문워크플로.취소가능검사
주문워크플로.취소가능검사.취소가능 --> 결제.message.매입분환불요청
주문워크플로.취소가능검사.취소가능 --> 결제.message.미매입결제취소요청
주문워크플로.취소가능검사.취소가능 --> 재고.message.예약삭제요청
주문워크플로.취소가능검사.취소가능 --> 주문.message.주문취소요청
주문워크플로.취소가능검사.취소가능 --> 이벤트버스.message.주문취소이벤트
```

- 관리화면이 주문 취소를 요청하면 주문워크플로가 주문, 이행, 결제 컬렉션 정보를 읽는다.
- 주문 서비스가 이 데이터를 돌려준다.
- 주문워크플로가 주문이 이미 취소되었는지, 완료되었는지, 취소되지 않은 이행이 남아 있는지 검사한다. 하나라도 해당하면 화면에 오류를 돌려주고 끝난다.
- 취소할 수 있으면 결제 서비스에 매입된 결제의 환불을 요청한다.
- 아직 매입되지 않은 결제는 취소를 요청한다. 이 요청은 실패해도 로그만 남긴다.
- 재고 서비스에 품목 예약 삭제를 요청한다.
- 크레딧 라인과 결제 컬렉션을 정리한 뒤, 주문 서비스에 주문 취소를 요청한다.
- 이벤트버스에 `order.canceled`를 묶어 둔다.

## 서비스 간 계약 요약

| 계약 | 생산자 → 소비자 | 형식·시점 | 실패·중복 처리 |
| --- | --- | --- | --- |
| 모듈 서비스 메서드 | 주문워크플로 → 각 모듈 | 같은 프로세스 안의 호출이며, 단계마다 독립 트랜잭션 | 단계가 실패하면 앞 단계의 보상을 역순으로 실행. 매입·환불 단계는 보상 없음 |
| 링크 생성·삭제 | 주문워크플로 → 링크 모듈 | `createRemoteLinkStep` | 보상 단계에서 링크 삭제 |
| 업무 이벤트 | 주문워크플로 → 이벤트버스 → 구독자 | `eventGroupId`로 묶어 두었다가 워크플로 성공 후 전달 | 실패하면 묶인 이벤트를 버림(`clearGroupedEvents`). 전달 보장 수준은 이벤트버스 구현을 따름 |
| 제공자 호출 | 결제·이행 모듈 → 외부 제공자 | 모듈 안에서 동기 호출 | 결제 웹훅은 `payment-webhook` 구독자가 처리 |
